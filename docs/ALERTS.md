# Сповіщення

## Умова

Файл `infra/main/monitoring.tf`, ресурс `aws_cloudwatch_metric_alarm.ecs_cpu_high`:

| Параметр | Значення |
| --- | --- |
| Метрика | `AWS/ECS` `CPUUtilization`, виміри `ClusterName`, `ServiceName` (сервіс застосунку) |
| Статистика, період | `Average`, 60 с |
| Умова | `> 70` у 2 періодах поспіль (`evaluation_periods = 2`), тобто CPU понад 70% протягом 2 хвилин |
| Відсутні дані | `notBreaching` |
| Дії | `alarm_actions` і `ok_actions` - SNS-топік `cloude-tech-lab1-alerts` |

Канал доставки - SNS-топік з підпискою `email` (`aws_sns_topic_subscription.email`). Лист приходить при
переході в ALARM і другий - при поверненні в OK. Підписку треба підтвердити за посиланням із листа, інакше
листи не доставляються.

Alarm на 5xx і на unhealthy targets з лабораторної роботи 1 лишилися без змін.

## Чому саме CPU > 70% протягом 2 хвилин

- Ціль автомасштабування - 60%. Якщо середній CPU тримається вище 70%, масштабування не встигає: нові задачі
  ще стартують або сервіс уже на максимумі (4 задачі). Саме про це треба знати людині.
- Вимога «протягом 2 хвилин» відсікає короткі сплески: одна хвилина з високим CPU (старт задачі, деплой,
  прогрів) не будить нікого вночі. Без неї alarm перемикався б ALARM/OK на кожному коливанні (flapping).
- Латентність p95 > 500 мс була б ближчою до відчуттів користувача, але в нашому сервісі вона не досягає
  500 мс навіть на насиченій задачі: у прогоні 1 найбільше p95 на ALB за хвилину - 388 мс. Такий alarm у
  тесті не спрацював би.

## Спрацювання під час прогонів

Дані з `aws cloudwatch describe-alarm-history --alarm-name cloude-tech-lab1-ecs-cpu-high`. Час UTC; за Києвом
+2 год, тобто вже 11.11.2026.

| | Прогін 1 (кеш вимкнено) | Прогін 2 (кеш увімкнено) |
| --- | --- | --- |
| Початок навантаження | 22:28:37 | 23:19:38 |
| Перша хвилина з CPU > 70% | 22:30 (84.5%) | 23:21 (84.8%) |
| Початок сталого навантаження | 22:31:37 | 23:22:38 |
| OK → ALARM (перший лист) | 22:34:38 | 23:25:38 |
| **Від початку сталого навантаження до ALARM** | **3 хв 01 с** | **3 хв 00 с** |
| Кінець навантаження | 22:38:37 | 23:29:38 |
| ALARM → OK (другий лист) | 22:39:38 | 23:29:38 |

В обох прогонах alarm пройшов ALARM і OK, тобто SNS надіслав обидва листи. У прогоні 1 OK настав через 1 хв після кінця навантаження, у прогоні 2 -
у момент кінця навантаження: з кешем друга задача швидше збила CPU нижче 70% (57.2% у хвилину 23:28).

## Звідки береться затримка

Умова alarm (2 хвилинні точки поспіль > 70%) уперше виконалася на точках 22:30 і 22:31, тобто не раніше
22:32:00. Перехід у ALARM відбувся о 22:34:38. У прогоні 2 точки 23:21 і 23:22, межа 23:23:00, ALARM о
23:25:38. Складові:

1. Сама умова: 2 періоди по 60 с. Поки не минуть 2 хвилини перевищення, alarm не спрацює. Це навмисно, щоб
   не було flapping.
2. Запізнення метрики: ECS публікує `CPUUtilization` у CloudWatch із запізненням, а alarm оцінюється раз на
   хвилину. В обох прогонах це однакові ~2 хв 38 с понад межу з п. 1.
3. Доставка: SNS надсилає лист одразу після переходу, далі - пошта (секунди, точний час видно на знімках).

Разом від реального перевищення порогу до листа - близько 4-5 хв, від початку сталого навантаження - 3 хв.

## Чи прийнятно це для реального сервісу

Для цього alarm - так. Він попереджувальний: перевантаження спершу має прибрати автомасштабування (друга
задача з'являлася через 1-2 хв після листа: 22:36:16 і 23:26:50), а людина потрібна, лише якщо воно не впорається. 3-5 хв реакції
для такого сигналу нормально.

Для аварійних сигналів (сервіс віддає помилки, латентність неприйнятна) 4-5 хв - забагато: користувачі весь
цей час бачать проблему. Там варто:

- стежити за тим, що бачить користувач: латентність p95/p99 і частка 5xx на ALB, а не CPU;
- брати умову «M із N» (наприклад, 2 з 3 точок) замість суворо поспіль, а для коротших періодів -
  метрики з високою роздільністю (10 с);
- слати сповіщення не лише на email, а в канал, який будить (SMS, PagerDuty, Slack).
