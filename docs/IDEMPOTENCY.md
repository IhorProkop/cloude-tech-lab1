# Ідемпотентність запису

## Яку проблему це розв'язує

`POST /tasks` не ідемпотентний: кожен виклик вставляє новий рядок. Проблема з'являється, коли клієнт не знає,
чи спрацював його запит:

- **таймаут**: запит дійшов, задачу вставлено, але відповідь загубилася (обрив мережі, клієнт чекав 5 с,
  а сервер відповів за 6 с, ALB закрив з'єднання). Клієнт бачить помилку і повторює запит - у базі дві
  однакові задачі;
- **автоматичні ретраї**: HTTP-клієнти, SDK, мобільні застосунки і проксі повторюють запит після помилки
  або 502/503. Під час деплою чи scale-in задача може зникнути саме між вставкою і відповіддю;
- **подвійне натискання** кнопки в інтерфейсі;
- **повторна доставка з черги** (бонус 6): обробник може отримати те саме повідомлення двічі.

Ідемпотентна операція при повторі дає той самий результат, що й перший виклик. За визначенням HTTP такими є
GET, HEAD, PUT, DELETE, OPTIONS (і TRACE), а POST і PATCH - ні. Заголовок `Idempotency-Key` робить POST
ідемпотентним: клієнт генерує унікальний ключ (наприклад UUID) один раз на операцію і передає його в усіх
повторах цієї операції.

## Як працює

Код - `app/src/idempotency.js`, використання - `POST /tasks` у `app/src/routes.js`.

1. Без заголовка `Idempotency-Key` поведінка як раніше: вставка і `201`, Redis для цього не потрібен.
2. Ключ перевіряється: 1-255 видимих ASCII-символів, інакше `400`. `title` перевіряється до звернення в
   Redis, тож запит з порожнім `title` відразу отримує `400` і нічого не зберігає.
3. Запис у Redis має ключ `idem:user:<sub з JWT>:<Idempotency-Key>`. Ключі окремі для кожного користувача:
   двоє користувачів з однаковим ключем не побачать відповідей один одного.
4. Відбиток запиту (fingerprint) - SHA-256 від назви операції і тіла з відсортованими ключами JSON. Він
   зберігається разом з відповіддю, щоб відрізнити справжній повтор від помилкового повторного використання
   ключа.
5. Сервер читає запис:
   - **запису немає** - ставить короткий lock: `SET key {"state":"pending",fingerprint} NX EX 30`. `NX`
     гарантує, що з двох одночасних запитів lock отримає лише один. Переможець вставляє задачу і перезаписує
     ключ на `{"state":"done",fingerprint,status,body}` з `EX 86400` (24 години);
   - **запис `done`, відбиток збігається** - повертає збережені статус і тіло без звернення до бази, із
     заголовком `Idempotency-Replayed: true`;
   - **запис `pending`, відбиток збігається** (одночасний дублікат) - чекає до 2 с, перевіряючи кожні 50 мс.
     Якщо за цей час з'явився `done` - повертає збережену відповідь, якщо ні - `409 Conflict`;
   - **відбиток інший** - `422 Unprocessable Entity`: той самий ключ з іншим тілом;
   - **Redis недоступний** - `503` з `Retry-After: 1`, вставка не виконується. Інакше сервер не зможе
     гарантувати, що це не повтор, а клієнт явно попросив цю гарантію.
6. Якщо вставка впала з помилкою (500), lock видаляється, і клієнт може повторити запит з тим самим ключем.
   Зберігаються лише успішні відповіді.

| Ситуація | Відповідь | Вставка в базу |
| --- | --- | --- |
| Без ключа | 201 | щоразу |
| Перший запит з ключем | 201, `Idempotency-Replayed: false` | так |
| Повтор з тим самим ключем і тілом | збережені статус і тіло, `Idempotency-Replayed: true` | ні |
| Одночасний дублікат | збережена відповідь або 409, якщо перший не встиг за 2 с | ні |
| Той самий ключ, інше тіло | 422 | ні |
| Некоректний ключ | 400 | ні |
| Ключ є, Redis недоступний | 503, `Retry-After: 1` | ні |

Опис заголовка і відповідей є в Swagger UI (`/docs`).

## Тест

Сценарій `loadtest/idempotency.js` (k6, 1 VU, одна ітерація). Запуск однією командою:

```powershell
.\loadtest\run.ps1 -Script idempotency.js -RunName idempotency-aws
```

Що перевіряє (13 перевірок, threshold `checks rate==1`, тож будь-яка невдача дає ненульовий код виходу):

1. два послідовні однакові POST з одним ключем: обидва 201, тіла однакові, другий має `Idempotency-Replayed: true`,
   у базі один рядок з цим `title`;
2. два одночасні однакові POST з одним ключем (`http.batch`): кожен 201 або 409, усі 201 мають однакове тіло,
   у базі один рядок;
3. той самий ключ з іншим тілом: 422, рядок не вставлено;
4. два POST без ключа: обидва 201, у базі два рядки (стара поведінка не змінилася);
5. некоректний ключ: 400.

Кількість рядків рахується через `GET /tasks`: `POST` інвалідує кеш списку, тож список читається з бази.

### Перевірка 409 і 503 локально

На `compose.yaml` з увімкненим Redis:

- lock `pending` з правильним відбитком поставлено вручну через `redis-cli SET ... EX 30`, ніби перший запит
  ще виконується. `POST` з тим самим ключем через 2.03 с отримав `409 {"error":"A request with this
  Idempotency-Key is still in progress"}`;
- `docker compose stop redis`: `POST` з ключем - `503`, `Retry-After: 1`, `{"error":"Idempotency store
  unavailable"}`; `POST` без ключа - `201`. Після `docker compose start redis` запит з тим самим ключем - `201`;
- `redis-cli TTL` для збереженої відповіді показав 85 807 с (24 години мінус час з моменту запису).

## Обмеження

- Відповідь записується в Redis після вставки в базу. Якщо Redis впаде саме між цими кроками, відповідь
  клієнту піде (201), але повтор вставить ще один рядок. Помилку видно в журналі (`Idempotency result save
  failed`).
- Lock живе 30 с. Якщо вставка триватиме довше, другий запит з тим самим ключем зможе виконатися.
- Redis у цьому проєкті без збереження на диск і з `maxmemory-policy allkeys-lru`: після перезапуску Redis
  або при нестачі пам'яті збережені відповіді зникають, і повтор після цього вставить новий рядок.
- Повністю надійний варіант - зберігати ключ у тій самій транзакції, що й задачу (колонка
  `idempotency_key` з унікальним індексом у PostgreSQL), а Redis лишити як швидкий шар для повторів.
  За умовою завдання використано Redis.

## Як це поєднується з чергою (бонус 6)

Черги на кшталт SQS доставляють повідомлення **щонайменше один раз**: обробник видаляє повідомлення лише після
успішної обробки, і якщо він упав, не встиг видалити повідомлення до кінця visibility timeout або SQS
доставив копію, те саме повідомлення буде оброблено вдруге. Без захисту це дало б дві задачі.

У бонусі 6 той самий механізм застосовано на двох рівнях:

- **клієнт → API**: `POST /tasks/async` теж приймає `Idempotency-Key`. Повтор після таймауту поверне ту саму
  відповідь `202` з тим самим id операції, і в чергу не піде друге повідомлення;
- **черга → обробник**: обробник викликає `idempotency.run` з ключем `job:<id операції>` і відбитком
  повідомлення. Перша обробка вставляє задачу і зберігає результат; повторна доставка того самого повідомлення
  отримує збережений результат (той самий id задачі) без нової вставки, просто оновлює статус і видаляє
  повідомлення. Якщо дві копії обробляються одночасно, друга бачить lock, і її повідомлення повертається
  в чергу до наступної спроби.

Отже, доставка «щонайменше один раз» плюс ідемпотентний обробник дають ефект «рівно один раз» для бази.
